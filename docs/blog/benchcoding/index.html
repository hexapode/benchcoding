Who owns the search?

Suppose you own a document parser. It works, but large tables are slow and scanned invoices still cause trouble. You could write ten optimization tickets. You could also give agents the current implementation, a way to measure it, and a budget to try alternatives.

Someone still has to decide which inputs matter, what counts as correct, and how much latency is worth trading for accuracy. Someone has to notice when the fastest submission silently stops parsing half the document. That person is the engineer responsible for the search.

I’m calling this Benchcoding: organizing agent work around a benchmark and a maintained leaderboard, with an engineer directing experiments and accepting the results. The name is provisional. The workflow is specific enough to try.

These workflows will coexist. A leaderboard is useful when you can measure an improvement repeatedly. It does little to tell you which product to build, whether an interface is understandable, or when a customer’s request points to a deeper problem.

The organizational change is ownership. A person can own parsing accuracy or inference cost while people elsewhere in the company contribute experiments. They bring their own hypotheses and allocated compute. The owner sets priorities, manages the board, and decides what gets integrated.

The public races are a starting point

Big O Speedrun tracks attempts to improve mathematical bounds. Its distinctions between Claimed, Human Verified, and Lean Verified matter as much as the ranking. For Lean verification, the site describes rebuilding a proof and checking that it establishes the exact intended statement. A proof of a subtly different theorem would miss the point. [1]

The Open Kernel Challenge offers a different version: improve GPU kernels against a reference implementation. The organizer describes correctness checks on fresh random inputs and timing against SGLang on the same hardware. Its serving track uses hidden conversation workloads. The competition makes both performance and the conditions of measurement explicit. [2]

These are examples of public, measurable work. They do not establish that companies have already reorganized around internal leaderboards. That move is the proposal: bring a similar loop inside a company, around a workload the company actually cares about.

An internal board needs more than a score. It needs the baseline revision, evaluation version, cost of the run, and evidence for each claim. It also needs access controls: employees contributing experiments should not automatically get unrestricted access to customer data or production systems.

What the engineer does on Monday

Start with the parser’s production workload. Freeze a baseline. Write down the objective: reduce processing time while preserving accuracy, memory limits, and the output contract. Decide which tradeoffs are allowed before the first run.

The engineer gives different groups of agents different questions. One explores image preprocessing. Another investigates table extraction. A third profiles repeated work. Each experiment runs in an isolated checkout, with a bounded budget and a record of what changed.

What does the review find?

“Skip hard pages” drops difficult inputs, so its speed gain is invalid. Reusing preprocessing passes the holdout checks and a clean replay; it is eligible for integration review. Batching table detection exceeds the memory limit. Nothing has been deployed.

The owner redirects effort after reading the evidence. The preprocessing approach may deserve more experiments. The skipped-page result calls for a better completeness check. Ten agents making the same caching change are a reason to change assignments, not to launch ten more.

When two candidates survive independently, test them together. Their gains may overlap, or one may invalidate the other’s assumptions. Only a reviewed, combined change becomes the next baseline. Production rollout still needs monitoring and a way back.

You need to understand what the agents are doing

A score cannot explain how an agent got there. Read the diffs and traces. Look at which files it inspected, which tests it ran, how it interpreted a failure, and whether it changed the problem to make the result easier.

Understanding behavior is practical engineering work. If several runs keep weakening the same assertion, the agent may have misunderstood the objective or found a gap in its incentives. If every run starts with the same approach, the search has little diversity. If an agent reports success without running the evaluator, its summary is not evidence.

The response depends on the cause. Clarify the allowed changes. Give different runs different starting hypotheses. Preserve failed experiments so the next run does not repeat them. Share a verified discovery without forcing every agent onto the same implementation.

Engineers will still write code. They may need to repair the harness, investigate a numerical error, or implement an architectural change that the agents have missed. Deciding when to intervene requires knowing the system well enough to judge the experiments.

Owning the leaderboard means being accountable for what its numbers mean.

The winning result deserves suspicion

“Cheating” here describes a result that exploits the evaluation instead of satisfying the intended task. It does not require a claim about an agent’s intentions. Hard-coded answers, leaked test data, skipped cases, weakened tolerances, and work moved outside a timer can all produce impressive scores.

Keep the evaluator outside the agent’s writable workspace. Run submissions with restricted permissions. Use fresh inputs and hidden holdouts, and audit any changes to the execution path. For asynchronous GPU work, check that timing includes completion; for caches, distinguish legitimate reuse from remembering evaluation answers.

A holdout also wears out. If repeated scores guide thousands of experiments, information about that set leaks through the feedback. Limit access to the final evaluation, refresh it deliberately, and keep a separate acceptance run. Record the evaluation version so results from different versions are not quietly ranked together.

Correctness checks can be wrong too. For a mathematical proof, someone must examine the statement and assumptions. For a parser, someone must decide whether the test set represents the documents customers send. No amount of agent compute repairs an objective that rewards the wrong behavior.

Inspect the runners-up as well. A suspicious winner may reveal a weakness affecting the whole board. When the harness changes, rerun the baseline and eligible candidates before comparing them again.

Try it on one problem

There is no need to build an internal compute market first. The engineer can allocate the budget directly. Start with one repository and one objective that has cheap, repeatable feedback.

  1. Define the contract.Choose a representative workload, baseline, acceptance constraints, and a fixed compute budget. Protect the final holdout.
  2. Make experiments replayable.Keep the source revision, model and configuration, tool trace, evaluation version, resource use, and raw results. Preserve failures.
  3. Give the owner useful controls.They must be able to stop a run, redirect effort, compare hypotheses, and inspect a candidate’s evidence. Begin with a simple board.
  4. Compare against task delegation.Run the same objective from the same baseline with an engineer assigning specific tasks. Give both workflows comparable compute and human time.
  5. Measure what survives.Compare independently accepted improvement per dollar and per hour of engineer attention. Count regressions, rejected claims, and the maintenance burden.

Repeat across several runs before drawing a conclusion. A lucky search is not a methodology. Include model inference, evaluator hardware, and failed attempts in the cost. Report the setup cost of the harness separately so reuse does not make the first experiment appear artificially cheap.

The result could be disappointing. Evaluation may cost more than the improvement is worth. Agents may converge on the same ideas. Integration may consume all the time saved. That would tell us where this workflow fails.

For a first trial, I would choose a slow component with a known workload and an engineer who understands its failure modes. Give that person a board, a budget, and a week. The question is whether the changes that survive their review justify doing it again.
