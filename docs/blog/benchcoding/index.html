An engineer responsible for the outcome

In the workflow I have in mind, the engineer responsible for a parser’s performance would spend part of the week choosing among experiments run by agents. Some runs would come from their own team; others could come from colleagues trying to fix a bottleneck in a service they depend on.

We already use benchmarks to guide optimization. The change I’m proposing is in how the work gets assigned: the engineer takes responsibility for a sustained search, with discretion over which approaches get more time, instead of specifying the implementation tasks for every attempt. Agents receive a working baseline and the conditions an improvement has to satisfy. The engineer then follows what they try closely enough to redirect the work.

I’m calling this Benchcoding. It seems most useful for problems such as parsing accuracy or inference cost, where a team can run a meaningful evaluation repeatedly. I wouldn’t expect a leaderboard to settle an argument about which product to build.

Consider a parser that struggles with large tables and scanned invoices. In a task-based workflow, an engineer might decide to add a preprocessing cache, write the ticket, and ask an agent to implement it. With Benchcoding, they might start by asking several agents to investigate why those documents are expensive, while another team contributes an approach it has already tried on a related service. Caching could still be the best answer, but the owner has left room for alternatives they didn’t think to assign.

Two ways to organize the same optimization work
QuestionTask delegationBenchcoding
Who defines the work?An engineer chooses an implementation task.An owner chooses an outcome and directs experiments over time.
What do agents receive?A bounded change to make, with acceptance criteria.A baseline, an evaluation contract, and an experiment budget.
How is success judged?The requested change passes review and its acceptance checks.The change improves the agreed outcome and passes review.
What happens next?The engineer assigns the next task.The owner uses the results to fund, redirect, or stop further attempts.

Both approaches need tests and code review, and either can use many agents. The practical question is whether giving the engineer a broader search to manage produces better results for the time and money spent.

What the board is for

The parser owner would first choose a representative workload and freeze a baseline. Suppose processing time is the objective, with accuracy and peak memory held within agreed limits. That gives contributors enough information to judge an idea before spending their budget on it.

A useful experiment log preserves the history of the work. The board adds a maintained view of what deserves attention now, so someone arriving from another team can decide what to try next. It shows the current baseline alongside active approaches, failed attempts, and candidates awaiting review. Each entry links to the code and evidence behind it, with the evaluation version and resources consumed.

That shared view changes a few decisions. Someone considering a preprocessing cache can see that three runs have already tried it and read why they failed. The owner can stop funding repeated variants of the same idea or assign another run to a promising result that hasn’t reproduced yet. When an improvement is accepted, everyone starts from the updated baseline rather than continuing to optimize an obsolete version.

What does the review find?

The fastest submission omits difficult pages. Reusing preprocessing still produces the expected output when replayed on held-out documents, so it can go forward for integration review. Batching table detection runs faster but exceeds the memory limit; its author would need to fix that before resubmitting.

After review, reusing preprocessing is the only new candidate eligible for integration. The apparently faster submission skipped difficult pages, and the batching approach exceeded the memory limit. Those failures should remain visible with their explanations: the batching idea may be useful later, while the skipped-page result exposes a missing check in the agent’s local evaluation.

A board that only sorts scores wouldn’t be enough. To justify maintaining it, it should reduce duplicate work and make it easier to choose the next experiment. I’d judge it partly by whether contributors can make those decisions without asking the owner for a private briefing every time.

Letting another team contribute

Suppose the team building invoice search notices that the parser spends a lot of time decoding the same images. They already maintain a cache for their own service and think the same approach might help. Through the board, they can find the parser’s current baseline, permitted inputs, and evaluation instructions, then use part of their team’s experiment allowance to test the idea.

The parser owner decides whether to fund follow-up runs from the parser budget. There is no need for an automatic market here; a person can make that call after looking at the evidence. Recording which team paid for each run makes the cost visible and prevents an apparently free contribution from hiding a large compute bill.

The search team has a reason to help because faster parsing would improve its own product. Other contributions might reuse knowledge from a neighboring service or investigate a problem an engineer finds interesting. I wouldn’t assume that making the board available will produce participation on its own. Teams need permission to spend time on it, and contributors should receive credit when their work is accepted.

Maintenance has to be settled before a merge. In this example, the parser team would own the accepted cache and its on-call consequences. If the change adds a dependency the team cannot support, a good benchmark result won’t make it worth taking.

Review could easily become the owner’s bottleneck. Contributors should submit enough evidence for another engineer to replay the result, and automated checks should reject obvious failures before they reach the review queue. Teammates can review candidates within an agreed scope, while the owner handles priorities and disputed tradeoffs. If submissions arrive faster than the team can evaluate them, stop new runs for a while.

The owner also needs to read agent traces, especially when a run behaves unexpectedly. Did the agent investigate the slow path, or repeatedly edit a test until it passed? Are several agents following the same unsuccessful approach? Those observations should influence the next assignments. Someone who understands the parser may need to write a small diagnostic or fix the evaluation before another round of agent work will help.

Owning the leaderboard means being accountable for what its numbers mean.

From public competitions to internal work

Big O Speedrun is one reason I think this is worth trying. It tracks attempts to improve mathematical bounds and separates Claimed, Human Verified, and Lean Verified results. Its description of Lean verification includes checking a proof against the intended problem statement, which matters if a submission proves a different, easier statement. Contributors can see both the current result and the kind of evidence supporting it. [1]

The Open Kernel Challenge applies a similar public format to GPU optimization. Its judging process describes fresh random inputs for correctness checks and comparison with SGLang on the same hardware. The serving track uses hidden conversation workloads. These details give entrants a common target while limiting some of the shortcuts a visible benchmark would invite. [2]

I expect companies to try internal versions of this arrangement. A parser team could publish a problem that colleagues understand well enough to contribute to, even if they don’t work in that repository every day. The public competitions suggest how to organize that participation; whether it pays off inside a company still needs testing.

An internal version has obligations beyond judging submissions. It needs a safe way to provide representative data, agreement about who reviews changes, and a team willing to maintain the result. Those requirements would affect which problems I put on the board in the first place.

Catching a misleading result

The skipped-page example is easy to spot once someone checks completeness. Other shortcuts take more investigation. An agent might move expensive work outside the timed region, relax a tolerance, or cache answers for known inputs. I’m using “cheating” to describe exploiting the evaluation this way, without making a claim about the agent’s intentions.

The evaluator should run outside the agent’s writable workspace, with permissions that prevent a submission from changing its tests or reading the final holdout. Reviewers need to reproduce the result from the submitted revision and inspect the code path being measured. For asynchronous GPU work, that includes checking that the timer waits for completion; for caching, it means understanding what can legitimately be reused in production.

Repeated feedback can also reveal information about a hidden test set. I would reserve a separate acceptance evaluation for promising candidates, limit how often it is queried, and refresh it deliberately. Every board entry needs the evaluation version so a harness change doesn’t leave incomparable results in the same ranking.

Even a well-protected evaluator can measure the wrong thing. The parser owner still has to ask whether the documents reflect customer traffic and whether the accuracy checks catch consequential failures. When a bad submission exposes a gap, fix the check and rerun the affected candidates, including the baseline.

Finally, improvements have to survive integration. Two changes that work independently may rely on conflicting assumptions or eliminate the same repeated work. Test their combination before promoting it to the baseline, then use a limited production rollout to check that the measured benefit holds up on real traffic.

A pilot worth continuing

I’d begin with one component whose workload is well understood. Give the engineer responsible for it a fixed experiment budget and enough time to inspect the runs. A simple board linked to versioned code and evaluation results is sufficient for this first trial.

The comparison should be ordinary task delegation on the same optimization problem, starting from the same baseline. In that version, an engineer chooses specific changes for agents to implement. Keep compute limits and available engineer time comparable, and repeat the comparison across several runs or components so one lucky discovery doesn’t decide the outcome.

Before starting, choose the improvement target and spending limits, including the cost assigned to engineer time. For the parser example, I’d propose these provisional criteria:

  • The accepted change reduces processing time by at least 10% on the agreed production workload, with no regression beyond the accuracy and memory limits set in advance.
  • Total cost stays within the pilot budget and accepted improvement per dollar is at least as good as task delegation. Count evaluation hardware and failed runs, along with setup, review, and integration time.
  • The parser team accepts responsibility for maintenance, and the result survives a limited production rollout.

The 10% target is an example to agree or replace before the trial, not a result or a universal threshold. Record setup costs separately as well as in the total, so the team can judge whether reuse would change the economics of a second round.

If the method clears those conditions, extend it to another component and see whether the advantage persists. If it generates a busy board but costs more for the same accepted improvement, keep task delegation. The next experiment would need to address a specific problem found in the pilot, such as duplicate attempts or excessive review time, before spending another round of budget.
